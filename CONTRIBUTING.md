# Contributing to Keelson

Thanks for helping. Keelson's instructions are read by many agents on many teams, so a small wording change can shift behaviour everywhere. We change them the way Keelson asks agents to change their own rules: **one specific change at a time, with evidence.**

## Ways to help
- **Feedback from real use:** what worked, what drifted, where it asked too much or too little. Use Discussions → *Feedback* or an issue.
- **Eval results:** run golden tasks (`core/keelson/evals/golden-tasks.md`) in your tool and post results with the *Eval result* issue form.
- **Playbook or role improvements:** one playbook/role per PR.
- **Lessons from your team:** a rule from your `lessons.md` that would help everyone (remove anything about your company or code first).
- **New stack profiles:** `profiles/<stack>.md` (Go, Java/Spring, Rails, .NET, mobile…).
- **New or better tool adapters:** see below.

## Repo layout
```
core/AGENTS.md            the persona (always loaded; keep it under 12,000 chars)
core/keelson/             playbooks, roles, evals, templates, models.yaml  → installed to .keelson/
core/seed/                team-owned files created once (memory, ACTIVE.md)
core/templates/           optional files users copy (CI workflow, MCP example)
profiles/                 stack profiles
adapters/<tool>/          per-tool glue; adapters/_agents/ = sub-agent definitions for all tools
lib/ bin/                 the npx installer (no dependencies)
skills/ plugins/ .claude-plugin/   GENERATED by `npm run build`; commit them
test/ scripts/            tests and repo checks
docs/                     roadmap, architecture, RFCs
```

## Rules for changes to instructions (`core/`, `adapters/`, `profiles/`)
1. **One purpose per PR.** One playbook, role, profile or adapter. Small diffs are reviewed faster and are easier to revert.
2. **Tool- and model-neutral core.** No tool names as requirements and no model names in `core/`; use *planner / builder / reviewer* and put mappings in `models.yaml`. `npm run check` enforces this.
3. **Evidence.** Describe the failure you saw (or the behaviour you want) and run at least 3 relevant golden tasks in one tool before and after. Paste the results in the PR. If no golden task covers it, add one.
4. **Don't weaken the non-negotiables** (honesty labels, approvals, evidence, untrusted-content handling, secrets, small changes). PRs that do will be closed.
5. **Keep it short.** Long instructions are followed less reliably. Prefer editing a line over adding a paragraph; move detail from `AGENTS.md` into a playbook.
6. **Plain words.** Write for an engineer reading quickly, not for a model. If a sentence needs a second read, rewrite it.

## Adding a tool adapter
- Put tool-specific files in `adapters/<tool>/` and wire them in `lib/install.js` (add to `TOOLS`).
- Generate sub-agents from `adapters/_agents/*.md` (one source for every tool) and models from `models.yaml`.
- Never overwrite user files: use managed blocks (`upsertBlock`) or `writeManaged`.
- Add the tool to the support table in the README, honestly: what's automatic and what's instruction-only.
- Add tests in `test/install.test.js`.

## Development
```bash
npm run build    # regenerate skills/, plugins/, .claude-plugin/, dist/chatgpt
npm run check    # portability and consistency checks
npm test         # installer tests + hook tests (needs bash, jq, git)
node bin/keelson.js init --dir /tmp/try --tools claude-code --yes
```
CI fails if generated files are stale, so run `npm run build` and commit the result.

## Bigger changes
New modes, changes to gates, the orchestration model or the installed layout need an RFC first: copy `docs/rfcs/0000-template.md`, open a PR, and discuss before implementing.

## Releases
Maintainers tag `vX.Y.Z`; CI publishes to npm with provenance. Breaking layout changes are major versions and come with an `update` path.
